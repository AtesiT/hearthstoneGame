# ЭТАП 0: АНАЛИЗ И ПЛАНИРОВАНИЕ

Проект: **EMBERFALL — «Пепел и Пламя»** — карточная игра для двоих по локальной сети, вдохновлённая Hearthstone, в пиксельном стиле.

Состояние репозитория на момент анализа: пустой проект (только `README.md`), Node.js v22.22.3, npm 10.9.8 доступны. Работа ведётся на ветке `arena/f90ae8ee-hearthstonegame`.

### 1.3 Самые сложные технические моменты (честно)

1. **Консистентность аур и баффов.** Статические эффекты («+1/+1 вашим другим существам») требуют: хранение базовых статов отдельно от наложенных; пересчёт при каждом изменении поля; корректный «откат» при смерти источника ауры; chain-смерти от deathrattle (рекурсия с ограничением глубины ~10). Решается единой функцией `recomputeBoard()` + event-driven обработкой смертей через очередь (без неограниченной рекурсии).
2. **Targeting-поток.** Одинаковая механика для 4 разных видов выбора: цель для заклинания, цель для battlecry, цель для атаки, выбор карты в руке. Сервер считает валидные цели при запросе и в каждом снапшоте; клиент — «инерционный» UI (подсветка + клик). Ошибки «нажал не в то время» гасятся повторной валидацией сервером.
3. **Reconnect-машина.** Состояния: `connected → disconnected(grace 30с) → reconnected | lost`. Клиент: `overlay "переподключение" (10 попыток × 1 с)`. Нужно корректно обработать: обрыв в лобби, обрыв в игре, обрыв обоих, reconnect в течение/после grace, повторный вход по коду (новый токен).
4. **Анимации по events.** Клиент получает событие «миньон A атаковал B на 4 урона» и должен: подвигать атакующего, показать вспышку, тряхнуть экран, показать число урона, удалить мёртвого с частицами — всё **до** того, как новое авторитетное состояние «перезапишет» сцену. Решается: события применяются к локальному render-state, потом — reconciliation с авторитетным состоянием (самоисцеляющийся рендер).
5. **Античит.** Рука/колода противника не должны попадать в сеть в принципе. Санитизация на сервере при отправке (не на клиенте!); seed RNG не передаётся; uid-ы карт в руке принадлежат только владельцу.

## 2. ВЫБОР ТЕХНОЛОГИЙ С ОБОСНОВАНИЕМ

### 2.1 Стек одним взглядом

| Слой | Выбор | Альтернативы | Почему |
|------|-------|--------------|--------|
| Runtime | **Node.js 22 (ESM)** | Python 3.11 | Один язык на весь стек; нативный ESM без сборки; `node --test` для тестов; `ws` — зрелая WS-библиотека |
| Сервер WS | **`ws` 8.x** | socket.io, raw http-upgrade | Минимум зависимостей (1 шт. на проект!), без «магии» socket.io (rooms/polling-fallback не нужны), предсказуемый API |
| HTTP/статика | **встроенный `node:http`** + ~60 строк своего статик-хендлера | Express, Fastify | Ещё меньше зависимостей; 3 типа контента (html/js/css/img) — Express избыточен |
| Фронтенд | **Vanilla JS (ESM в браузере) + DOM/CSS** | React, Vue, Svelte | Нет build-шага вообще; сцена игры мала (≤14 юнитов + 10 карт в руке); DOM даёт бесплатный layout, текст, доступность; CSS-трансформы — GPU-анимации; React добавил бы сборку и не дал бы выигрыша в анимациях |
| Рендеринг эффектов | **Canvas 2D overlay** (pointer-events: none) поверх DOM | PixiJS, чистый Canvas, SVG | Частицы/молнии/искры — 200–500 частиц — Canvas тянет на 60 fps легко; PixiJS избыточен (WebGL, ~300 КБ) для такой сцены; SVG не для частиц |
| UI/анимации карт | **DOM + CSS transitions/keyframes** | всё в Canvas | Чёткий пиксельный текст, лёгкий layout руки/доски, `transform: translate()` — аппаратное ускорение, простая отладка |
| Шрифт | **Press Start 2P через `@fontsource/press-start-2p` (npm)** | Google Fonts CDN | Игра работает **без интернета** (LAN) — CDN не вариант; npm-пакет даёт woff2, который коммитится в репозиторий. Проверено: пакет существует и весит ~90 КБ |
| Арты | **AI-генерированный пиксель-арт (256×256, коммит в репо)** + процедурный фолбэк в коде | Чистый кодовый пиксель-арт, внешние ассеты | 30 уникальных артов в коде выглядели бы «шарповато»; единый промпт-шаблон даёт консистентность; ассеты статичны → LAN-дружелюбно; фолбэк гарантирует работоспособность при битых ассетах |
| Звук | **Web Audio API, 100% процедурно** (square/triangle/noise + секвенсор) | OGG/MP3 файлы | Чиптюн идеально синтезируется осцилляторами; 0 КБ ассетов; гарантированно 8-bit звучание; две фоновые музыки — таблички нот + look-ahead секвенсор |
| Тесты | **`node --test` (встроенный)** + headless-симуляция 2 WS-клиентов | Jest, Mocha | Ноль зависимостей; движок — чистые функции → легко тестировать; симуляция полной случайной игры — сильный end-to-end тест |
| Типы | **JSDoc-аннотации** в JS | TypeScript | TypeScript потребовал бы build-шага (tsc) или ts-node (ещё одна зависимость) — против требования «запуск одной командой без деплой-магии». JSDoc даёт IDE-подсветку и документацию типов без компиляции |

### 2.2 Backend: почему Node.js (а не Python)

1. **Один язык на клиент и сервер** — общие константы протокола и карточный DB живут в `shared/` и используются и в Node, и в браузере как ESM.
2. **`ws`** — самая распространённая и стабильная WS-библиотека для Node; Python-вариант (`websockets`/FastAPI) тоже хорош, но тогда клиент (JS) и сервер (Python) — два экосистемных контекста, две системы типов, две системы тестов.
3. **Статика + WS из одного процесса** — один `npm start` поднимает всё на одном порту 8080. У Python-варианта та же схема работает, но Node даёт чуть меньше обрядов (нет uvicorn/gunicorn-разговоров).
4. **`node --test`** — встроенный тестовый раннер (Node 22), без установок.
5. **Производительность** не имеет значения для 2 игроков, важен **просто-и-надёжно** — Node выигрывает по «одна команда, одна зависимость».

### 2.3 Сетевая библиотека: `ws`

- Raw WebSocket поверх HTTP-апгрейда: минимум overhead, полный контроль.
- Никакого автосоздания rooms/namespace-магии socket.io — rooms мы делаем сами (они и есть игровые комнаты, а не транспортные сущности).
- Ошибка клиента не роняет сервер: обёртка try/catch на каждое сообщение + `terminate()` на аномалиях.

### 2.4 Frontend: почему Vanilla JS (а не React/Vue)

- **Нет сборки** → нет `vite/webpack/parcel` → нет `node_modules` на клиенте, нет кэшей, нет «почему у меня не запускается dev-сервер». `npm start` = сервер раздаёт статику.
- Масштаб UI: 6 экранов, десятки DOM-элементов. Это «одна большая страница» — классическая область Vanilla. Состояние клиента маленькое и плоское (`viewState` + UI-состояние: выбранная карта, режим прицеливания).
- **Анимации**: React перерисовывает дерево; здесь проще и быстрее управлять конкретными DOM-нодами напрямую (карта = `<div>` с `transform`, анимация = CSS-переход + `transitionend`).
- Разработчикам проще отлаживать «голый» DOM, чем виртуальный.

### 2.5 Рендеринг: DOM + CSS + Canvas overlay (гибрид)

| Что рендерим | Где | Почему |
|--------------|-----|--------|
| Карты в руке, миньоны, герои, портреты, HP/мана, кнопки | DOM | Layout, текст (пиксельный шрифт чёткий на DOM), hover/клик, CSS-переходы для движения (GPU) |
| Числа урона, баннеры «ВАШ ХОД», пузыри эмоций | DOM (absolute) | Чёткий пиксельный текст, простая жизнь (spawn → animate → remove) |
| Частицы (смерть, огонь, лёд, конфетти), молнии, искры | Canvas overlay, `pointer-events: none` | Сотни мелких элементов в 60 fps — DOM бы задыхался, Canvas — нет |
| Тряска экрана | CSS `transform` на контейнере стола | Аппаратно, не бьёт по layout |
| Красная вспышка урона героя | DOM overlay div, opacity-анимация | Простота |

**Почему не PixiJS / чистый Canvas**: сцена ≤ 30 анимируемых узлов — это не экшен на 60fps-объектов; DOM даёт бесплатно: доступность, чёткий текст, hover-состояния, легкость пиксельного CSS-стиля (жёсткие рамки, `image-rendering: pixelated`). Canvas — только там, где он сильнее (частицы, молнии).

### 2.6 Офлайн-принципы (критично для LAN)

Ничто в рантайме не ходит в интернет:
- шрифт — в репо (`public/assets/fonts/`);
- арты — в репо (`public/assets/cards/`, `heroes/`, `bg/`);
- звук — синтезируется;
- зависимости — 2 шт. (`ws`, `@fontsource/press-start-2p`), ставятся при `npm install` один раз.

### 2.7 Звуковой движок

`public/js/audio/`:
- `sfx.js` — синтез: `blip()` (клик), `play()` (миньон: низкий square + noise-тёх), `spell()` (арпеджио up), `weapon()` (metallic: noise + резонансный triangle), `attack()` (whoosh: filtered noise sweep + impact), `death()` (падающее арпеджио), `heroHurt()` (низкий boom), `draw()` (быстрый swish), `turn()` (2 ноты), `win()`/`lose()` (фанфары мажор/минор), `emotion()` (8 разных бипов).
- `music.js` — секвенсор: таблица нот `[midi, dur, vol, ch]`, look-ahead scheduling (каждые 25 мс планируем ноты на 0.12 с вперёд) — без джиттера. Две темы: menu (8 тактов, A-minor pentatonic, медл.) и battle (16 тактов, быстрее, другой мотив). Fade-переходы при смене экрана. Mute/volume — `localStorage`.

### 3.2 Разделение ответственности

| Что | Сервер | Клиент |
|-----|--------|--------|
| Правила игры, валидация команд | ✅ **весь** | ❌ никогда |
| RNG (shufle, random-мишени) | ✅ seed в GameState | ❌ |
| Содержание чужой руки/колоды | ✅ хранит, **не отправляет** | ❌ не знает |
| Времена ходов (start/turn/mana) | ✅ | ❌ |
| Рендер, анимации, звук, FX | ❌ | ✅ весь |
| Выбор «что нажать» (targeting UI) | ❌ (но присылает `validTargets`) | ✅ |
| Отправка команд | приём + атомарное применение | формирование |
| Обрывы/reconnect | grace 30 с, итог партии | 10 попыток × 1 с |

**Правило**: клиент знает только то, что видит на экране. Всё остальное — домысел, который сервер отклонит.

### 3.3 Где хранится состояние игры

- **Единственный источник истины: сервер.** `Room.game: GameState` живёт в памяти процесса Node.
- Сервер после **каждой** успешной команды пересчитывает состояние, пушит event(s) в `events[]` и рассылает обоим игрокам **санитизированные снапшоты** (`sanitizeState(state, seat)` — у каждого свой, т.к. руки разные).
- Клиент хранит `viewState` — свою проекцию. Локальный рендер-state (позиции DOM-узлов) может кратковременно «опережать» снапшот ради анимаций; после применения анимаций — reconciliation: рендер-state приводится к `viewState` (самоисцеление).
- **Почему полная синхронизация, а не дельты**: LAN-задержка < 1 мс, снапшот ~3–8 КБ JSON — пропускная способность не важна. Полное состояние = рассинхрон невозможен в принципе (дельты требуют управления версионированием, ретрансляций, catch-up — усложнение без выигрыша).
- **Почему нет prediction/interpolation на клиенте**: клиент не считает правила — нечего предсказывать; команды применяются сервером за < 1 мс, латентность незаметна.

### 3.4 Как предотвращаем читерство

1. **Нет игровой логики на клиенте.** Клиент не может «изменить» HP/ману/карты — у него их нет в логическом смысле; только `viewState` для рендера.
2. **Секреты не уходят в сеть.** `sanitizeState` (выполняется на сервере при отправке) заменяет чужую руку на `handCount`, чужую/свою колоду на `deckCount`, вырезает `rngSeed`. Рука отправляется **только владельцу**.
3. **Команды, а не состояния.** Клиент отправляет `{type:'play_card', handUid, targetUid}` — сервер ищет этот uid в руке **именно этого игрока**, проверяет: чей ход, есть ли мана, мана достаточна, цель легальна (для taunt-целей, board full и т.д.). Всё или ничего: нет валидации → `error`, состояние не тронуто (атомарность: валидация до изменений).
4. **RNG — только сервер.** Shufle колод и «случайные» мишени эффектов — `mulberry32(seed)` в GameState; seed не передаётся клиентам до конца игры (можно показать в конце партии).
5. **uid-ы вместо «карт».** Клиент не говорит «сыграй Fireball» — он говорит «сыграй карту с uid `abc123`», а сервер знает, что это. Перепутать/подменить невозможно.
6. **Rate-limit эмоций/команд** (1 msg/50 мс на игрока) — защита от флуда и спам-атак на сервер.
7. **Открытый код клиента — не угроза**: даже прочитав весь JS, читер не найдёт там ни правил, ни секретов — есть только рендер и отправка команд.
8. **Проверка**: в §7 — критерий «читерство через консоль невозможно» + тест: клиент-симулятор шлёт нелегальные команды (чужая карта, атака вне хода, атака сквозь taunt, игра без маны) — все должны быть отклонены, состояние не должно измениться.

### 4.5 Сериализация и приватность

- Формат: JSON-текст WS-фрейма. Обёртка: `{"t": "<message_type>", "d": <payload>}` (короткие ключи — меньше байт, удобно на сетке).
- Один и тот же `GameState` → **два** снапшота (`self/opp` меняются местами). Составляется на сервере функцией `sanitizeState(state, forSeat)`.
- Проверка (тест): JSON снапшота игрока 0 не содержит uid/карты из руки и колоды игрока 1 и не содержит `rngSeed` (assert на парсинг).
- Прочие сообщения (лобби) не содержат секретов.

### 4.6 История ходов (журнал событий)

- `GameState.events` — monotononic-журнал со `seq`. Каждый снапшот несёт события с `seq > lastSeq`, который клиент подтвердил полем `ack` в следующем сообщении (клиент присылает `ack` с каждым ходовым сообщением, например с `ping`).
- **Откат (undo) не нужен**: команды атомарны (валидация до изменений) и необратимы по дизайну (как в HS). Журнал нужен для: (1) инкрементальной рассылки событий; (2) повторного синхронизированного входа (reconnect: сервер шлёт все события с `min(clientLastSeq, head)`, при отсутствии — полный снапшот); (3) отладки/повтора («реплей»: прогнать journal по пустому состоянию — тестовый режим); (4) будущих зрителей.
- Журнал не чистится в течение партии (партия ≤ ~200 событий, ~50 КБ — ничто).

## 5. СЕТЕВОЙ ПРОТОКОЛ

### 5.1 Транспорт

- WebSocket на `ws://<host>:8080` (тот же порт, что и HTTP-статика; апгрейд на `/ws`).
- Сообщения — JSON-текст. Максимальный размер фрейма: 64 КБ (защита от мусора).
- `ping`/`pong` каждые 20 с (сервер закрывает «мёртвые» соединения за 40 с без трафика).

### 5.2 Клиент → Сервер (все типы)

| t | payload | Когда | Валидация сервером |
|---|---------|-------|--------------------|
| `hello` | `{nick}` | сразу после подключения | nick 3–16 симв.; создаёт session |
| `create_room` | `{nick}` | меню → «Создать комнату» | session без комнаты |
| `list_rooms` | `{}` | экран лобби | — |
| `join_room` | `{code, nick}` | лобби → ввод кода | код существует, seat свободен, фаза=lobby |
| `leave_room` | `{}` | «Выход» | — (в игре = сдача? нет: в игре это disconnect-поток) |
| `toggle_ready` | `{ready: bool}` | комната ожидания | сид занят мной |
| `start_game` | `{}` | хост, когда оба ready | я сид 0, оба ready, фаза=lobby |
| `play_card` | `{handUid, targetUid?, targetSeat?, ack}` | игра, мой ход | полный legality-пакет (§3.4.3) |
| `attack` | `{fromUid, fromSeat, toUid, toSeat, ack}` | игра, мой ход | чей ход; from — мой миньон/оружие; canAttack; taunt; target существует |
| `end_turn` | `{ack}` | игра, мой ход | чей ход |
| `send_emotion` | `{emotion, ack}` | игра, любой момент | throttling 1/с; emotion из 8 |
| `request_state` | `{}` | reconnect / потеря sync | — (сервер ответит полным снапшотом) |
| `ping` | `{ack}` | каждые 5 с / keepalive | — |
| `reconnect` | `{roomCode, token}` | после обрыва, до `hello` | токен совпадает с сидом в grace |

`ack` — seq последнего события, который клиент увидел (сервер знает, с какого seq слать новые).

### 5.3 Сервер → Клиент (все типы)

| t | payload | Когда |
|---|---------|-------|
| `welcome` | `{session, name, serverTime}` | на `hello` |
| `rooms` | `{rooms: [{code, host, players, phase}]}` | на `list_rooms` и при каждом изменении (broadcast всем в лобби) |
| `room_update` | `{code, phase, seats: [{nick, ready, connected}], mySeat}` | любое изменение комнаты |
| `state` | `ViewState` (§4.3) | после каждой команды + turn-тики |
| `game_start` | `ViewState` (первый) | старт партии (клиент переключает экран) |
| `error` | `{code, msg}` | нелегальная команда (клиент показывает toast, состояние не менялось) |
| `kicked` | `{reason: 'room_closed'|'duplicate_token'|'full'}` | вытеснение (двойной вход по тому же токену, закрытие комнаты) |
| `bye` | `{msg}` | закрытие сервера |
| `pong` | `{t: pingTime}` | на `ping` |

Коды `error`: `not_your_turn`, `not_enough_mana`, `card_not_yours`, `invalid_target`, `taunt_blocked`, `board_full`, `hand_full_warning`, `unit_not_mine`, `cannot_attack` (sickness/frozen), `no_weapon`, `game_over`, `bad_payload`, `throttled`.

### 5.4 Обработка рассинхронизации

1. **Базовый случай** (99%): команда → сервер валидирует → применяет → снапшот с новыми событиями. Клиент: применяет события (анимации), затем reconciliation рендера к снапшоту.
2. **Потеря снапшота** (редко, LAN): клиент не получил `state` (таймаут 2 с после отправки команды) → `request_state` → сервер шлёт полный снапшот (без потери: состояние — истина).
3. **Пропуск событий** (ack «отстал»): сервер включает в следующий снапшот все события от `ack+1` (до 50 шт.; дальше — полный снапшот без анимаций прошлого).
4. **Защита от повторных команд**: клиент не дублирует (команда — по клику, не polling); сервер идемпотентен по сути: повтор `end_turn` вне своего хода = `not_your_turn`, без побочных эффектов.
5. **Версия протокола** `v: 1` в снапшоте: при несовпадении клиент показывает «нужна новая версия клиента».

### 5.5 Обрыв соединения и reconnect

**Сервер:**
- WS close → если игрок в комнате: `seats[i].connId = null`, `player.disconnected = true`, `opp_left` обоим, запуск grace-таймера **30 с**.
- Если `phase === 'game'`: партия **не** завершается сразу — ждём reconnect (противник видит баннер «Оппонент отключился… N с»).
- Grace истёк: `phase === 'game'` → `game_over`, победил подключённый (`opponent_left`), `opp_left` финальный. `phase === 'lobby'` → сид освобождается.
- Комната с 0 игроков удаляется через 60 с.

**Клиент:**
- Обрыв WS → overlay «Переподключение… 10 с», попытки каждые 1 с: `hello` + `reconnect {roomCode, token}` (токен в `localStorage`, ключ `emberfall:tok:<code>`).
- Успех → сервер: полный снапшот + `opp_back` обоим.
- 10 неудач → «Соединение потеряно» + кнопка «В меню» (игра, по правилам, засчитана противнику — сервер уже решил).

**Двойной вход по токену** (открыл на втором устройстве): новый conn получает `kicked duplicate_token`… нет — наоборот: новый вход **вытесняет** старое соединение (стандартное поведение), старому — `kicked`.

**Оба отключились в игре**: grace обоих идёт; кто вернётся первым — видит «Оппонент покинул игру» через 30 с (партия засчитана).

### 5.6 Коды комнат и ники

- Код: 5 символов из `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (без 0/O/1/I/L — путаницы). Коллизии почти невозможны; при коллизии — генерируется другой.
- Ник: 3–16 символов `[A-Za-zА-Яа-яЁё0-9_]`, трим. Дубли в комнате запрещены (ошибка).
- Сервер при старте печатает: `Играть: http://192.168.1.10:8080` (обход `os.networkInterfaces()`, все IPv4) — хост просто диктует адрес другу.

## Приложение Б. Правила игры (кратко, для движка)

1. **Старт:** колоды (по 30 карт, одна из каждой из 30) тасуются серверным RNG; оба игрока тянут по 3 карты; **второй** игрок получает Монету зари в руку; первый ход — случайный.
2. **Начало хода:** `maxMana = min(10, maxMana+1)`, `mana = maxMana`; тянуть 1 карту (рука > 10 → карта сгорает + звук/событие `burn`; колода пуста → fatigue-урон своему герою, +1 за каждое); все свои миньоны: `canAttack = true`, `frozen = false`. **Исключение (HS-модель, баланс Этапа 6):** первый игрок НЕ тянет на своём самом первом ходу — это +карта для второго вместе с Монетой компенсирует преимущество темпо.
3. **Разыгрывание:** карта из руки, мана ≥ cost; миньон — на доску (≤ 7), summoning sickness (кроме Charge); оружие — на героя (заменяет старое, старое ломается); заклинание — эффект (с целью/без); battlecry — после размещения.
4. **Атака:** миньон (canAttack, не frozen) → существо противника или герой (обязательный Taunt — если есть); герой с оружием → аналогично; после атаки: `canAttack=false`, оружие: `durability−1` (0 → сломалось); Poisonous: миньон с Poisonous, атакуя существо, всегда убивает его (урон 1+); Divine Shield жертвы поглощает первый инстанс урона (любой величины) и ломается.
5. **Смерть миньона:** убрать с доски → deathrattle (может убить других → очередь, глубина ≤ 10) → `recomputeBoard()` (ауры).
6. **Победа:** HP героя ≤ 0. Одновременная (теоретически) — побеждает атакующий/активный. Отключение оппонента (grace истёк) — победа подключённого.
7. **Оглушение (статус):** миньон не может атаковать до начала своего следующего хода. Применяется: `frost_elemental` (battlecry), `frost_lance` (спелл).
8. **Таргет-правила:** точечные урональные спеллы (`fireball`, `spark_bolt`, `frost_lance`) обязаны попадать в Taunt, если он есть (как в HS); AoE игнорирует Taunt.
9. **Эмоции:** 8 шт., не чаще 1/с, видны обоим, не влияют на игру.
10. **Fatigue:** если колода пуста, «тянуть» = урон `fatigue+1` своему герою.
